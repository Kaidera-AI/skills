# Container and pod engineering

## The principle

Treat the image and the Pod as one delivery contract. Optimize for compatibility, reproducibility, least privilege, startup and shutdown correctness, observability, and measured cost. Image size matters, but a smaller image that recompiles native dependencies, lacks required trust data, cannot terminate cleanly, or forces unsafe debugging is not an optimization.

Use upstream OCI and Kubernetes behavior. Do not make a cloud-managed build, registry, security, or runtime service a core dependency. Run the workspace `cloud-agnostic-policy`, `infra-naming-gate`, and `deploy-gate` whenever their triggers apply.

## The trigger

Invoke this skill when:

- authoring or reviewing a Dockerfile, Containerfile, `.dockerignore`, or image-build workflow;
- selecting or changing a base image, libc family, runtime image, image architecture, tag, or digest;
- packaging native Python, Node.js, Go, Rust, Java, or system-library dependencies;
- deciding whether processes belong in one container, multiple containers in one Pod, or separate workloads;
- creating or changing a Pod template, probes, resources, security contexts, volumes, service accounts, lifecycle hooks, or termination behavior;
- investigating slow builds, oversized images, architecture failures, crash loops, failed probes, stuck termination, or image drift; or
- preparing an image or Pod for a deployment handoff.

Do not invoke this skill for:

- host or VM design that does not package or run a containerized workload;
- application-only changes that do not affect the image or Pod contract; or
- live deployment authorization. This skill produces evidence; the deployment gate still controls environment mutation.

## The steps

1. **Read the whole delivery surface before changing it.** Inspect the Dockerfile or Containerfile, `.dockerignore`, lockfiles, build workflow, image references, Helm/Kustomize output, workload controller, service account, target inventory, target Kubernetes version, and existing validation commands. Never infer CPU architecture or libc compatibility from an environment label. -> verify: the review names the source files, target architectures, runtime requirements, and current image reference from fresh evidence.

2. **Choose the base from a compatibility matrix, not a size ranking.** Use a trusted, maintained base that contains only the runtime capabilities the workload needs. Prefer a slim glibc-based variant when native dependency compatibility is unproven. Alpine is acceptable only when musl compatibility, binary availability, build time, and runtime behavior pass on every target architecture. Distroless or `scratch` is acceptable only when the artifact is compatible and certificates, users, time-zone data, diagnostics, and incident access are explicitly handled. -> verify: cold build plus runtime tests pass for each target architecture, and the selected base has a documented compatibility reason.

3. **Make the build reproducible and cache-efficient.** Use named multi-stage builds. Copy dependency manifests and lockfiles before frequently changing source. Use deterministic package-manager commands and the repository's existing BuildKit cache pattern. Keep `.dockerignore` next to the build context and exclude VCS data, local dependencies, logs, test output, credentials, environment files, editor state, and generated artifacts not required by the build. Never pass secrets through `ARG`, `ENV`, or copied files; use the existing secret-mount or CI custody path. -> verify: a source-only change reuses the dependency layer, the reported build context is bounded, and no secret appears in image history or layers.

4. **Keep the runtime stage operationally minimal.** Copy only runtime artifacts and required data from the builder. Run as a dedicated non-root numeric UID/GID. Use exec-form `ENTRYPOINT` or `CMD`, make PID 1 propagate signals and reap children, write logs to stdout/stderr, and declare writable paths. Remove compilers, package caches, package managers, and shells unless a measured runtime or incident requirement justifies them. -> verify: image history contains no build toolchain or secret material, the process runs as the expected UID, and `docker stop` or the equivalent sends a clean termination signal within the stated grace period.

5. **Choose the process boundary deliberately.** Default to one concern per container, not one operating-system process by decree. Multiple processes in one container are acceptable only when they share release, scaling, failure, security, and lifecycle boundaries and a tested init or process supervisor owns signals, reaping, logs, and exit behavior. In Kubernetes, put tightly coupled helpers that must share network or storage in the same Pod; use an init container for finite setup and a native sidecar for a continuing helper whose lifecycle needs that behavior. Put independently scalable, releasable, privileged, or failure-isolated concerns in separate workloads. -> verify: the review records one of `single-container`, `multi-process-container`, `multi-container-pod`, or `separate-workloads` and explains lifecycle, scaling, failure, and security boundaries.

6. **Pin identity and plan updates together.** Use a readable version tag plus an immutable digest for base images and deployed images. A digest without a refresh process freezes security fixes, so record the owner and cadence or automation that proposes tested digest updates. Derive multi-platform output from verified target inventory; do not publish an architecture that was not built and exercised. -> verify: `docker buildx imagetools inspect` or the registry-neutral equivalent shows the expected digest and platform set, and the update path is named.

7. **Define the Pod as a restricted, observable contract.** Start from Kubernetes Pod Security Restricted defaults: `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, `seccompProfile.type: RuntimeDefault`, and drop `ALL` capabilities. Prefer `readOnlyRootFilesystem: true` with explicit ephemeral or persistent writable mounts. Disable service-account token mounting unless the workload calls the Kubernetes API. Set measured CPU, memory, and ephemeral-storage requests/limits; use startup, readiness, and liveness probes for their distinct purposes; define termination grace and `PreStop` only when required; source secrets through the approved custody mechanism. -> verify: rendered manifests pass the repository's schema/policy checks, every exception has an owner and reason, and probe plus termination behavior is exercised rather than inferred from YAML.

8. **Validate the artifact, not just the source.** Build every declared platform, run unit and integration tests against the produced image, inspect layers and metadata, generate the repository-standard SBOM, run the existing vulnerability and policy scans, and test startup, readiness, liveness failure, signal handling, and writable paths. Render the final manifests and use server-side dry run only against an authorized cluster. -> verify: the evidence records exact image digest, platforms, size, scan result, SBOM reference, test commands, rendered-manifest result, and unresolved exceptions.

9. **Return a bounded verdict.** Use `references/review-checklist.md`. Report `PASS`, `CONDITIONAL`, or `BLOCKED`; separate required fixes from optional optimization; include rollback and digest update implications. Do not convert a review into a deploy. -> verify: the handoff contains the verdict, exact artifacts, evidence commands, exceptions, and next authorized action.

## Decision rules

### Base image

- Use slim/glibc by default for Python or Node.js workloads with unproven native dependencies.
- Use Alpine only after musl-native dependency and performance evidence passes on every target architecture.
- Use distroless when the application and incident model do not require a shell or package manager and all runtime data is present.
- Use `scratch` only for a genuinely compatible static artifact with explicit CA, user, time-zone, and debug decisions.
- Never select a base solely because it has the smallest compressed size.

### Process placement

- Same lifecycle, scale, release, trust, and failure unit: one container may be reasonable.
- Same Pod lifecycle and shared network/storage, but independently managed processes: use multiple containers in one Pod.
- Finite setup that must finish first: use an init container.
- Continuing helper with ordered Pod lifecycle: use a native sidecar when the target Kubernetes version supports it.
- Independent scale, release, security, ownership, or availability: use separate workloads.

### Probe purpose

- Startup: has initialization completed enough for periodic probes to begin?
- Readiness: should this instance receive work now?
- Liveness: is this instance irrecoverably stuck and safe to restart?
- Do not make liveness fail for a recoverable downstream dependency outage; that can create a restart cascade.

## The trade-off

This skill spends more time on compatibility, lifecycle, and evidence than a quick Dockerfile cleanup. It often rejects the absolute smallest image and may retain a small runtime tool or glibc-based layer when that reduces build risk and incident time. In return, builds are faster after normal source changes, artifacts are reproducible, Pods fail predictably, and deployment evidence is reviewable.

Suppress or narrow this skill when:

- producing a disposable local-only experiment that will never enter CI or a shared registry; or
- auditing a third-party image without permission or source to rebuild it. In that case, report observable risk without inventing a Dockerfile.

## Anti-patterns

- **Alpine by reflex.** Small compressed size does not prove musl compatibility, binary-wheel availability, build speed, or runtime performance.
- **Digest pinning without refresh.** Reproducible today, permanently stale tomorrow.
- **`COPY . .` without a reviewed `.dockerignore`.** Readable syntax is not the problem; uncontrolled build context is.
- **Dependency install after source copy.** Every source edit invalidates the expensive layer.
- **Build tools in the runtime stage.** Multi-stage syntax that still copies the toolchain has not reduced the runtime attack surface.
- **Secrets in build args or environment instructions.** Layer history is not secret custody.
- **Supervisor as a default inside Kubernetes.** It hides lifecycle and health boundaries that a multi-container Pod or separate workload may express directly.
- **One process dogma.** Splitting tightly coupled processes without analyzing lifecycle can add failure modes without adding isolation.
- **Tag-only deployment.** The same manifest can resolve to different bytes later.
- **Identical readiness and liveness checks by habit.** Traffic eligibility and restart safety are different questions.
- **Resource limits copied from another service.** Unmeasured values create throttling, eviction, or wasted capacity.
- **Manifest-only proof.** Security context, probes, and graceful termination are claims until exercised against the built image.

# Container and pod review checklist

Load this checklist for a concrete Dockerfile, Containerfile, OCI image, or Kubernetes workload review. Mark each item `pass`, `exception`, `fail`, or `not-applicable`. Never turn `not inspected` into `pass`.

## 1. Intake evidence

Record:

- repository, branch, and exact revision;
- Dockerfile or Containerfile path and build-context path;
- `.dockerignore`, lockfiles, build workflow, and deployment-manifest paths;
- target environments, Kubernetes versions, CPU architectures, and libc/runtime constraints from fresh inventory;
- image registry/repository, readable tag, immutable digest, and platform manifest;
- workload controller, namespace, service account, and owning team; and
- deployment authority status. A review does not imply deployment approval.

## 2. Image build

- Base is trusted, maintained, minimal for the requirement, and compatible with target architectures and native dependencies.
- Alpine has explicit musl evidence; distroless or `scratch` has explicit CA/user/time-zone/diagnostic decisions.
- Every base uses a readable version plus digest.
- A tested update mechanism or named owner refreshes pinned digests.
- Multi-stage build leaves compilers, headers, package caches, test output, and source-only material behind.
- Lockfile or dependency manifest is copied before source that changes frequently.
- Dependency installation is deterministic (`npm ci`, frozen lockfile, hash-checked or equivalent project command).
- `.dockerignore` excludes at least VCS metadata, local dependency directories, environment files, credentials, logs, caches, test output, and unrelated build artifacts.
- Build secrets use the approved secret-mount/custody path and do not appear in `ARG`, `ENV`, copied files, history, or layers.
- Package indexes and temporary package-manager data are removed in the same layer that creates them when relevant.
- Declared platforms are built from the same reviewed source and represented in the final image index.

## 3. Runtime image

- Runtime contains only the executable/application, required libraries, trust data, and intentional diagnostics.
- A dedicated numeric non-root UID/GID owns only the required paths.
- `ENTRYPOINT`/`CMD` uses exec form unless a tested wrapper is required.
- PID 1 propagates `SIGTERM`, reaps child processes, and returns meaningful exit status.
- Logs go to stdout/stderr; log files inside the image are not the only evidence path.
- Writable paths are explicit and map to `emptyDir`, persistent storage, or another approved volume where needed.
- Application starts with an empty writable volume and a read-only root filesystem when claimed.
- Runtime configuration and secrets are injected at run time, not baked into layers.
- Image labels and generated provenance identify source revision and build.
- SBOM and vulnerability/policy scan use the repository's established tooling. If none exists, report the gap rather than silently introducing a new dependency.

## 4. Process and Pod boundary

Record exactly one placement decision:

- `single-container`: one concern, or child processes owned by one service;
- `multi-process-container`: identical release/scale/failure/trust lifecycle with tested supervisor/init behavior;
- `multi-container-pod`: tightly coupled containers sharing Pod network/storage and lifecycle;
- `init-container`: finite setup must complete before application startup;
- `native-sidecar`: continuing helper needs ordered sidecar lifecycle on a supported Kubernetes version; or
- `separate-workloads`: independent release, scale, failure, security, availability, or ownership.

Verify:

- failure of each process/container has a defined effect on Pod readiness and restart;
- startup and shutdown order are explicit where order matters;
- scaling the primary does not unintentionally over-scale a heavyweight helper;
- a privileged helper does not expand the primary container's privilege boundary;
- logs and metrics identify the failing process/container; and
- Jobs can complete when a continuing helper is present.

## 5. Kubernetes workload

- Workload image is pinned by digest; no mutable tag is the sole identity.
- `runAsNonRoot: true` and no container sets UID 0.
- `allowPrivilegeEscalation: false` for every app, init, sidecar, and ephemeral container.
- `seccompProfile.type: RuntimeDefault` or an approved `Localhost` profile.
- Capabilities drop `ALL`; only `NET_BIND_SERVICE` may be added under Restricted policy, with a reason.
- `readOnlyRootFilesystem: true` where feasible; any exception names exact writable paths and why mounts cannot satisfy them.
- No `privileged`, host PID/IPC, unapproved host networking/ports, or `hostPath` volume.
- Service-account token automount is disabled unless Kubernetes API access is required.
- Service account and RBAC are workload-specific and least privilege.
- CPU, memory, and ephemeral-storage requests and limits are evidence-based; sidecar resources are included in Pod totals.
- Startup probe protects slow initialization when needed.
- Readiness removes an instance from service during temporary inability to accept work.
- Liveness detects only an irrecoverable local state that a restart can fix.
- Probe timeouts, periods, and thresholds match observed startup and response distributions.
- Termination grace covers request draining, checkpoint/flush, and sidecar ordering.
- `PreStop` is used only when application signal handling alone cannot satisfy shutdown behavior.
- Config and secret references use approved custody; no cleartext secret appears in manifest or values.
- Network policy, disruption budget, topology, storage, and rollout settings match the workload's availability contract where applicable.

## 6. Evidence commands

Adapt commands to the repository's established tooling. Never paste a live credential into a command or artifact.

```bash
docker buildx build --platform <verified-platform> --load -t <local-test-tag> -f <dockerfile> <context>
docker image inspect <local-test-tag>
docker history --no-trunc <local-test-tag>
docker run --rm --read-only --tmpfs <writable-path> <local-test-tag> <health-or-smoke-command>
docker buildx imagetools inspect <registry-image>@sha256:<digest>
helm template <release> <chart> -f <values>
kubectl apply --dry-run=server -f <rendered-manifest>
```

Also capture, using the repository's existing commands:

- cold build and source-only warm rebuild timings;
- build-context transfer size;
- unit/integration/smoke results against the built image;
- SBOM identifier and vulnerability/policy scan summary;
- startup-to-ready timing;
- readiness withdrawal during a temporary fault;
- liveness restart during an induced local deadlock only when safe;
- `SIGTERM` to clean exit timing; and
- rendered schema/policy validation.

Server-side dry run contacts a cluster. Use it only against an authorized target and report `not-run` when no authorized cluster is available.
