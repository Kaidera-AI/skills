# Doorbell

A doorbell is a small background program. Every 30 seconds it asks Cortex which AI Workers of a project have an **open handoff row**, and for each one it **types one fixed line into that worker's Orca terminal**, but only if the terminal is idle and nobody is typing. The line carries no work. It says "you have N open handoff(s), first `<id>`, check your queue", and the worker reads the real task from its Cortex queue.

Why it exists: without it, a lead creates a row and then a human has to click into each worker's tab to wake it. With it, a row wakes its worker by itself, and a pane that cannot be rung (busy for hours, waiting at an approval prompt) is reported instead of ignored.

There are three roles. Read the one that applies to you.

## 1. If you are a WORKER and the doorbell rang you

The line looks like this:

> Doorbell (lead@project): you have N open Cortex handoff(s), first `<id>`. Check your queue: `CORTEX_AGENT=<you> CORTEX_AUTH_TOKEN_FILE=… cortex-handoff --mine <you>`

Do this:

1. Run the command in the line. It lists your open rows. Read the one named `first`, and read the others.
2. **Claim a row you will work**: `cortex-handoff --claim <id> --agent <you>`. A claimed row **never rings again**. An unclaimed row rings again about every 30 minutes. So claim what you start, and claim a row you are deferring on purpose to silence it.
3. Do the work and return it: `cortex-handoff --return <id> --agent <you> --outcome completed --summary "…"`. Put the evidence in the summary. A return is a real write: it is not a dry run.
4. If a row is not yours, or is stale, say so in a return on that row. Do not leave it open: it will keep ringing.
5. Do not type back into the lead's pane. The answer goes in the row.

Your pane must be **titled with your worker name** (for example `vera`, `vera | project`, `Cortex-boot vera`): the doorbell finds you by title. If two panes carry your name, or one title names two workers, you are skipped, not rung.

## 2. If you are a LEAD or OPERATOR running a doorbell

Daily use:

- Status: `systemctl --user status doorbell`. Log: `tail -f <state_dir>/doorbell.log`. Attention log: `<state_dir>/attention.log` (lines starting `STUCK?` mean a pane is busy and silent, or is waiting at an approval prompt: **read that pane** with `orca terminal read --terminal <handle>`; do not trust "busy").
- **Stop typing at once, without restarting:** `touch <state_dir>/doorbell.off`. Resume: delete that file. The switch is read before every keystroke.
- Add a worker: add the name to `workers` in the config, then restart the service.
- A new row rings at once. A service restart rings once for each worker with open rows.

Full day-to-day and troubleshooting: `references/operating-and-troubleshooting.md`.

## 3. If you are INSTALLING it on a new project or VM

Follow `references/setup-new-project.md`. In short: build the Rust program from `assets/doorbell-src/`, copy `assets/doorbell.toml.template` and fill it in (project, lead, the lead's token file, the Orca workspace path, the workers), **run it once in dry run with its own state directory**, read what it says it WOULD ring, then install the service **in dry run**, and switch it live only when the project owner says so.

## Rules that are not optional

1. **Never run the program with a guessed flag, and never without `--config`.** The argument parser ignores unknown flags, so `--help` or a typo **starts a LIVE run**, and without `--config` it falls back to the path baked into the source (the helix project's), which on a machine that has that file starts a second live doorbell for the wrong project. Always: `doorbell --dry-run --once --config <your config>`.
2. **Dry run first, with its own `state_dir`.** A dry run that shares the live state directory shares the live kill switch and the live log.
3. **Lead's token only.** The doorbell reads every queue with the lead's token. It never reads a worker's token.
4. **One fixed line, never row text.** If you change the code, keep it that way.
5. **A ring that misfires: stop first, explain after.** `touch` the kill switch, then investigate.
6. **A pane reader must prove the screen ENDS at the input box.** After a terminal UI exits, its last frame stays on screen with a shell prompt under it. See `references/safety-and-lessons.md`.

# doorbell.toml: every setting

The doorbell reads one TOML file, given with `--config <path>`. Nothing else configures it. Copy `assets/doorbell.toml.template` and fill it in.

## Required

| Setting | Meaning |
|---|---|
| `api_url` | the Cortex API the doorbell asks, for example `http://localhost:8501` (the API answers `401` without a token: that means it is up) |
| `project` | the Cortex project key, for example `helix` or `tam`. It is also printed in the ring line and used in the token path shown to workers |
| `lead` | the lead's name, for example `kai` or `keith`. It is printed in the ring line. **The lead's own terminal is never rung** (a human types there): do not list the lead in `workers` |
| `lead_token_file` | the lead's Cortex token **file** (the doorbell reads every queue with it and never reads a worker's token). Mode 0600. Never put the token itself in the config |
| `workspace_path` | the Orca workspace (worktree path) whose terminals may be rung. Terminals of other workspaces are ignored |
| `since_utc` | `YYYY-MM-DD HH:MM:SS` UTC. **Rows created before this time are history and never ring.** Set it to the day you install: a restored or imported project can hold hundreds of old open rows |
| `poll_secs` | how often it asks Cortex, in seconds (30 is right) |
| `rering_secs` | an UNCLAIMED row rings again after this many seconds (1800 = 30 minutes). A CLAIMED row never re-rings |
| `state_dir` | where it writes `doorbell.log`, `attention.log` and where it looks for the kill switch `doorbell.off`. **A dry run must use its OWN `state_dir`** |
| `workers` | the worker names to ring, for example `["phoenix", "marvin", "sophia"]` |

## Optional

| Setting | Default | Meaning |
|---|---|---|
| `aliases` | none | a table mapping an exact pane title to a worker, for terminals whose harness sets a title with no worker name, for example `"π - helix" = "quill"` |
| `stuck_secs` | 1200 | a pane Orca calls busy, with open rows and no output for this long, is reported in `attention.log` (never typed into) |
| `attention_titles` | none | title fragments a harness shows while it waits for a human, for example `["Action Required"]` (Codex shows `[ ! ] Action Required` at an approval prompt). A busy pane with such a title is reported at once |
| `quiet_secs` | 20 | a pane is never typed into unless its output has been quiet for this long (a human's keystrokes repaint the pane, an idle agent does not) |
| `ring_unverified` | none | workers whose harness the input-box reader does not know. Empty by default: **a pane it cannot read is never typed into**. A listed worker is still held for a draft, a composer draft or recent output |

## Command line

```
doorbell --config <path> [--dry-run] [--once]
```

- `--dry-run`: log `WOULD RING …` and type nothing.
- `--once`: run one cycle and exit.
- **No other flag exists.** An unknown flag (`--help`, `-h`, a typo) is silently ignored and the program **starts a live run**. Without `--config` it uses the path baked into the source (the helix project's). Always pass `--config`, and for any first run pass `--dry-run --once`.

## What it checks before it types (all must pass)

1. The kill switch file `<state_dir>/doorbell.off` does not exist (checked again right before every keystroke).
2. The worker has an open row created at or after `since_utc` that has not already rung (or whose `rering_secs` passed while still unclaimed).
3. **Exactly one** terminal in `workspace_path` names the worker (whole word in the title, or an `aliases` entry). Two terminals, or a title that names two workers: skipped.
4. Orca says the terminal is idle, and the screen it reads shows the harness's input box **empty** with exactly the harness's footer rows under it (Claude Code, Codex and pi are known), and Orca's composer holds no draft, and the output was quiet for `quiet_secs`.
5. Anything it cannot tell is a hold, never a ring.

# Operating the doorbell, and what its log lines mean

## What rings and when

- Every `poll_secs` (30 s) it lists each worker's `pending` and `claimed` rows from Cortex with the lead's token.
- A worker is rung when it has an open row created at or after `since_utc` that has not rung yet. A **new row rings at once**.
- An **unclaimed** row rings again every `rering_secs` (30 minutes). A **claimed** row never re-rings. A worker silences a row it is deferring by claiming it.
- A service restart rings once for each worker that has open rows.
- It types exactly one fixed line and Enter. The line names the number of open rows and the first id. It never contains row text.

## Pane naming

A pane belongs to a worker when **exactly one** worker name appears in its title as a whole word: `phoenix`, `vera | helix` (Codex), `Run cortex-boot mike | helix`, `Cortex-boot cox` (Claude Code), `π - quill - helix` (pi). Two panes naming the same worker, or one title naming two workers, are skipped. A title that names no worker can be mapped in `[aliases]`. The lead's own pane is never rung (leave the lead out of `workers`).

## Log lines (`<state_dir>/doorbell.log`)

| Line contains | Meaning | What to do |
|---|---|---|
| `WOULD RING` | dry run: this is what it would type | nothing; this is the proof you want before going live |
| `RING` / `rang` | it typed the line | nothing |
| `busy, not ringing` | Orca says the pane is mid-turn | nothing; it tries again next cycle. If it stays busy for hours, see attention.log |
| `no single terminal titled 'x'` | no pane, or two panes, name worker x | open or rename the tab so exactly one carries the name |
| `skip cycle (no typing): …` | Orca (or the Cortex call) was not reachable; nothing was typed | start the Orca runtime / check `orca status` |
| `lead token unreadable` | the lead's token file is missing, unreadable or rotated | fix the file; the doorbell cannot read any queue without it |
| `must hold` (human-typing guard) | a draft, a composer draft or recent output: it held instead of typing | nothing; a human may be typing |

## Attention log (`<state_dir>/attention.log`)

A line `STUCK? <worker>: <why>, N open row(s); not typing - lead to look` means the pane is busy (or waiting at an approval prompt) and the doorbell will not type into it. Two reasons appear:

- the pane title contains one of your `attention_titles` (Codex: `Action Required`): the worker is waiting at an **approval prompt** that only a human can answer;
- Orca says busy but there has been **no output for `stuck_secs`** (20 minutes by default): Orca's idle check can stay false on a plainly idle pane. **Read the pane before you decide** (`orca terminal read --terminal <handle>`): a pane that looks busy to Orca may be idle, waiting for another worker, or really stuck.

A lead's watcher can tail this file and print each new line.

## Common jobs

- **Is it alive?** `systemctl --user status doorbell` and the last lines of `doorbell.log` (a cycle every 30 s).
- **Stop typing now:** `touch <state_dir>/doorbell.off`. The file is read before every keystroke. Delete it to resume.
- **Add or remove a worker:** edit `workers`, then `systemctl --user restart doorbell` (a restart rings once for each worker with open rows).
- **Ring one worker by hand** (the doorbell missed it, or it is a one-off): read the pane, check it is writable and idle with an empty input box, then `orca terminal send --terminal <handle> --enter --text "<one direct order naming the row id and the first step>"`. Never type into a pane you have not read first, and never type the row's text.
- **A row that never reaches the worker:** check, in this order: the row's `to_agent` is the worker's name; the row is newer than `since_utc`; exactly one terminal names the worker; the worker's pane is not holding a draft in Orca's composer (a composer draft silences a pane: only a human can clear it).

## Two limits you should know

- It cannot ring a pane whose harness it cannot read (an unknown harness, or a changed layout). It reports that as a hold, never as a ring. Add the worker to `ring_unverified` only if you accept ringing on the other guards alone.
- A worker that finishes a task at an empty prompt can still miss its next row if its own queue watcher expired or its composer holds a draft. If a lane waits for another lane for longer than a few minutes, **read the other lane's pane**.

# Safety rules and the two mistakes they come from

The doorbell types into other agents' terminals. A mistake is not a bug in a log: it is keystrokes in a live session. These rules are the result of two real mistakes (6 Nov 2026, during the Pi and Codex deployment on the helix project).

## Mistake 1: a guessed flag started a LIVE run

The author ran the built program with `--help`. It has no such flag. Its argument parser is three `args.iter().any(...)` lines, so **anything unknown is ignored** and the program started a live run with the default config, whose `state_dir` was the live state directory and whose token was the lead's. It ran 11 seconds and typed nothing, by luck (every pane was busy).

**Rules:**

1. **Never run a built program with a guessed flag next to live state.** Read the argument parser first.
2. **Always pass `--config` and, for any first run, `--dry-run --once`.**
3. **A dry run uses its OWN `state_dir`**, never the live one (it shares the kill switch and the log).
4. The same holds for any tool that can act: check how it parses its arguments before you run it.

## Mistake 2: a screen reader that did not prove the screen ENDS at the input box

After a terminal UI (pi, Claude Code) exits, its **last frame stays on the screen** with the shell prompt underneath, and Orca still reports the old identity from the title. The input-box reader saw "an empty box with at least two rows after the bottom rule" in that stale frame and the doorbell typed the ring into bash (a syntax error; nothing ran, again by luck).

**Rules:**

1. **An empty input box needs EXACTLY the harness's footer rows under it** (pi 2, Claude Code 2, Codex 2), not "at least". Anything else is a hold.
2. Write the test from the **real dead-pane shape** first (a stale frame with a shell prompt under it), then the happy case.
3. A dry run does not prove a pane that is busy in that cycle (the gate never reads it), so every deployment also needs a **read-only live report per pane**: read each pane once and say what the reader sees.

## The rule that governs a misfire

**If a ring misfires, stop the NEW binary first and say so.** Stop typing with the kill switch (`touch <state_dir>/doorbell.off`, and in every state directory a second instance uses), put the previous binary back, restart, then lift the switch. Write times with `date -u`, never from memory.

## Standing rules

- **Lead's token only.** The doorbell never reads a worker's token. Never copy a token between projects or agents.
- **No row text in the ring.** The job lives in the handoff. A ring that carries text is a way to smuggle instructions into another agent's session.
- **A pane it cannot read is never typed into.**
- **One doorbell per project.** Two doorbells ringing the same pane double the rings and confuse the re-ring bookkeeping.
- **Go live only on the project owner's word**, and note the time and the first ring.
- **Do not weaken a guard to make a ring happen.** If a worker is never rung, fix the naming, the harness support or the pane, not the guard.

# Setting the doorbell up for a new project (or a new VM)

Do these in order. Do not skip the dry run.

## 0. What you need

- An Orca runtime on the host, and the `orca` command line (normally `~/.orca/cli/bin/orca`). Check: `~/.orca/cli/bin/orca terminal list --json` lists your terminals.
- The terminals you want to ring are **Orca terminals on this same host**, in one workspace, each **titled with the worker's name**.
- `cortex-handoff` and a Cortex API reachable from this host (`curl -s -o /dev/null -w '%{http_code}' http://localhost:8501/health` gives `401` or `200`).
- The lead's Cortex token as a file (never printed, mode 0600). For a project `P` and a lead `L` the Kaidera convention is `~/.kaidera-os/cortex-auth/KOS-Cortex/P/L.token`.
- `cargo` (Rust) to build, `systemctl --user` to run as a service.

## 1. Put the source in the project

```
mkdir -p ~/DevVault/<project>/ops
cp -r <this skill>/assets/doorbell-src ~/DevVault/<project>/ops/doorbell
cd ~/DevVault/<project>/ops/doorbell
cargo build --release            # about a minute; the binary is target/release/doorbell
```

Optional: `cargo test` (the source carries its own tests; they use fake panes and never type into anything).

Keep the git commit and file hashes in `assets/SOURCE.txt` with the copy, so the next person knows which version this is.

## 2. Write the config

```
cp <this skill>/assets/doorbell.toml.template ~/DevVault/<project>/ops/doorbell/doorbell.toml
```

Fill in `project`, `lead`, `lead_token_file`, `workspace_path`, `since_utc` (**today**), `state_dir` and `workers`. Every setting is explained in `config-reference.md`. For a worked example see `assets/examples/tam.doorbell.toml.example`.

Name the terminals: open or rename each worker's terminal so that its title names exactly one worker (`phoenix`, `marvin | tam`, `Cortex-boot sophia` all work).

## 3. Dry run, ONCE, with its own state directory

```
mkdir -p ~/DevVault/<project>/ops/doorbell/state-dryrun
sed 's#^state_dir = .*#state_dir = "/home/azureuser/DevVault/<project>/ops/doorbell/state-dryrun"#' doorbell.toml > doorbell.dryrun.toml
PATH=$HOME/.orca/cli/bin:$PATH ./target/release/doorbell --dry-run --once --config ./doorbell.dryrun.toml
cat state-dryrun/doorbell.log
```

Read the log. You want, for each worker that has an open row, a `WOULD RING` line, and for the others a reason (`busy, not ringing`, `no single terminal titled 'x'`). **If it says `lead token unreadable` or `skip cycle (no typing)`, fix that first.** A dry run types nothing.

## 4. Install the service, in dry run

```
mkdir -p ~/.config/systemd/user
sed -e 's#@PROJECT@#<project>#g' -e 's#@LEAD@#<lead>#g' -e 's#@DIR@#/home/azureuser/DevVault/<project>/ops/doorbell#g' \
  <this skill>/assets/doorbell.service.template > ~/.config/systemd/user/doorbell.service
systemctl --user daemon-reload
systemctl --user enable --now doorbell
systemctl --user status doorbell
```

The unit starts with `--dry-run`. Watch `state/doorbell.log` for a few cycles.

## 5. Go live (only on the project owner's word)

```
systemctl --user edit doorbell
```
add, exactly:
```
[Service]
ExecStart=
ExecStart=/home/azureuser/DevVault/<project>/ops/doorbell/target/release/doorbell --config /home/azureuser/DevVault/<project>/ops/doorbell/doorbell.toml
```
then `systemctl --user restart doorbell`. The first ring comes within one cycle. Note the time and the first worker rung in the log.

## 6. Roll back, stop, or pause

- **Pause typing instantly:** `touch <state_dir>/doorbell.off` (delete it to resume).
- **Back to dry run:** delete the override (`~/.config/systemd/user/doorbell.service.d/*.conf`), `systemctl --user daemon-reload`, `systemctl --user restart doorbell`.
- **Stop completely:** `systemctl --user stop doorbell`.

## 7. Tell the workers

Give each worker the skill (the worker section of `SKILL.md`): when the doorbell line appears, run its command, **claim** the row you start, return it with evidence. Name their terminals exactly.
