# project-plan-create — epic decomposition + project-plan bootstrap

This is the planning method for a PM/lead worker. It serves two callers:

1. The **recurring PM planning beat** — a scheduled handoff (capability
   `pm-planning-beat`, mode `epic-decompose`) that spawns you once per interval to
   advance the active epic.
2. The **plan-bootstrap CTA** — "Ask lead to create project plan" when a project
   has no operating plan yet.

You run as an isolated, spawned process. Do **one** coherent planning action, then
STOP. The scheduler re-triggers on the next interval — do NOT loop or recurse
inside this run.

## Scope and isolation (read first)

- Operate ONLY in the `CORTEX_PROJECT` from `cortex-boot`. Your identity is
  `<you>@<project>`; use that exact form in every log, handoff summary, and
  progress note.
- Project isolation is absolute. Never read or mutate another project's Cortex
  rows. Every command runs in the spawned `CORTEX_PROJECT` only.
- Resolve the project, active epic, roster, and assignees from live state
  (`cortex-boot`, `cortex-handoff`, `cortex-search`). NEVER hardcode a project
  key, a worker name, or a role roster.
- Planning is **read-only on source**. Do not edit implementation code while
  planning. The deliverable is handoffs, plan files, and Cortex memory.
- Register skills and write handoffs only through the `cortex-*` CLIs / Cortex
  API — never by mutating Cortex Postgres directly.

## Step 1 — Boot (mandatory first commands)

```bash
cortex-boot <you>
cortex-handoff --mine <you>
```

From `cortex-boot` extract: the current project identity (use `<you>@<project>`),
the active epic name/ID and current increment, the live roster + roles (so you
assign by capability, not by a baked name), and any pending handoffs already
addressed to you (including `[WATCHDOG-SIGNAL]` handoffs).

## Step 2 — Assess the active epic

```bash
cortex-handoff --mine <you>
cortex-search "<active epic name>"
```

Assess:

1. **Done** — which handoffs are completed (terminal status only; a claim is NOT
   done — require visible evidence).
2. **In-flight** — which are claimed/running but not terminal.
3. **Pending / waiting** — which are open and unclaimed.
4. **Blocked** — anything stuck, failed, or carrying a `[WATCHDOG-SIGNAL]`.
5. **Wave / dependency state** — which waves are complete; which wave is now
   active.
6. **Signals** — any `[WATCHDOG-SIGNAL]` or override handoffs addressed to you.

## Step 3 — Decompose

Turn the active epic/increment into the **smallest coherent worker tasks**:

- **Assignee** — pick by capability/role from the live roster (e.g. a full-stack
  worker, a QA/validation worker, a deterministic worker). Resolve names from the
  roster; never hardcode them.
- **Dependency / wave** — order tasks so a task only dispatches after its
  predecessors are terminal. Independent tasks in the same wave may run in
  parallel.
- **Acceptance + Verify** — every handoff names exact files/scope, acceptance
  criteria, and a concrete Verify command (the test/command that proves it).

If **no operating plan exists yet** (bootstrap path), FIRST produce the plan:
write `docs/plans/<slug>/plan.mdx` using the `visual-plan` skill (operating plan,
recommended waves/increments, missing-information questions, and the handoffs the
plan implies). Then decompose from that plan.

### Optional wave sequencing rows

To make children dispatch in order, you may write `handoff_orchestration` rows
(the app-DB wave plan the dispatcher's wave-gate reads) so a later wave waits for
an earlier one. If you write none, every handoff is wave 0 (dispatched
immediately, backward-compatible).

## How to file handoffs — THE contract (read before Step 4)

You do **NOT** run `cortex-handoff --create` yourself. Instead, **EMIT** every
handoff you want filed as **ONE JSON block at the very end of your reply**, between
these exact sentinels. Your parent process (the app — unsandboxed + deterministic)
**files them for you** via the Cortex API and reports the created ids. This works
reliably regardless of your shell environment, so never assume filing is blocked
or sandboxed — just emit the block. Filed handoffs are **gated for human approval**
before they run.

```
===FILE-HANDOFFS===
[
  {"summary": "<you>@<project> DISPATCH — <inc>: <what to do>; Verify: <test>",
   "to_role": "<worker-role>", "priority": "high", "wave": 0,
   "acceptance": "<how to verify done>", "context": "<scope + dependencies>"}
]
===END-FILE-HANDOFFS===
```

Block rules: a JSON **array** of objects; each MUST have `summary` + `to_role`;
optional `to_agent`, `priority` (`low|medium|high|urgent`), `wave` (int, for
sequencing), `acceptance`, `context`. Emit **exactly one** block, covering only
THIS beat's handoffs (respect the budget). If you have nothing to file (epic done,
or only a watchdog-complete), emit **no** block at all.

## Step 4 — Act (exactly one action this beat, up to the stated budget)

The triggering handoff states a budget ("act at most N times this beat"). Default
N = 1. Choose ONE of:

### (a) Handle a watchdog signal (priority)

If a `[WATCHDOG-SIGNAL]` handoff is open and addressed to you, handle it BEFORE
filing new work. Identify the stuck handoff ID + reason, then choose one and EMIT
a handoff spec for it in the block:

- **Retry** — likely transient stall: emit a spec to the SAME role so a fresh run
  picks it up (summary: `RETRY — <inc>: <orig_id[:8]>; reason: <reason>`).
- **Reassign** — wrong fit / unavailable worker: emit a spec to a DIFFERENT role.
- **Escalate** — ambiguous, or the DLQ guard tripped (after N retries on the same
  handoff): emit a spec to the lead role instead of retrying again.

You MAY close the originating signal so it is not reprocessed (this is a complete,
not a create, and your parent already completes your triggering handoff):

```bash
cortex-handoff --complete <watchdog_signal_handoff_id>
```

### (b) File the next safe handoff(s)

Conditions: no unhandled watchdog signal; the wave/dep state allows it; NO
equivalent open handoff exists; visible evidence confirms predecessors are
terminal. EMIT one spec per handoff in the block — set `to_role`, a clear
`summary` (`DISPATCH — <inc>: <what>; Verify: <test command>`), and `wave` for
sequencing. Do not duplicate an already-open handoff.

### (c) Escalate to the lead (blocked / ambiguous)

A genuinely-blocked handoff or ambiguous epic direction (not a watchdog signal):
emit ONE spec to the lead role with `priority: "urgent"` and a `summary` of
`BLOCKED — <reason>; options: A <option-a>, B <option-b>`.

### (d) Epic complete — log and stop

All handoffs in the current epic/increment are terminal and there is no planned
next increment requiring a PM dispatch. Require visible terminal status on every
handoff, then:

```bash
cortex-log <you> decision "<you>@<project> EPIC-DONE — <epic>: all increments terminal; no next action"
```

Do NOT create a new handoff when the epic is done.

## Hard rules (loop guards)

- **List open handoffs before creating any.** Skip equivalents — this is
  belt-and-braces with Cortex create-dedupe.
- **NEVER create a `pm-planning-beat` / self-targeted planning handoff.** The
  scheduler owns the cadence. Re-filing one would create a planning loop.
- **One beat = up to the stated budget, then STOP.** Do not re-assess or chain a
  second round in the same run.
- **Evidence before done.** Never treat a handoff as complete without a terminal
  status visible in Cortex.
- **DLQ guard.** Never retry the same stuck handoff indefinitely; after the retry
  cap, escalate to the lead.
- **Identity everywhere.** Every summary/log uses `<you>@<project>` from
  `cortex-boot`.
- **No PR / deploy / tag preempt.** Surface READY-FOR-* handoffs to the lead;
  never open a PR or deploy without explicit approval.
- **Project isolation.** Every command runs in the spawned `CORTEX_PROJECT`.
