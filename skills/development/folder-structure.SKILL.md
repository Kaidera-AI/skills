# Folder structure

This skill gives a project a single, readable definition of where its work belongs. It helps a worker classify a new file and gives a project lead a safe process for adopting the layout. It is a portable candidate: it does not replace the project's own approved rules, grant file access, or perform a migration.

For a plain-language explanation for people, read the [human guide](#file-references-human-guide-md); the rules in this skill still govern.

## Start with the project's authority

Before creating or moving a project file, read the project's current `structure.yaml`, the accepted plan for the change, the project root and product catalogue registered by its owner, and the selected project shape. The bundled `references/structure.yaml` is a starter definition, not proof that a project adopted it. A project may use it only after its owner approves the layout and records the effective definition in the project's normal source of truth. Select `single_product` only when exactly one product is registered; otherwise use `multi_product`. For ordinary placement in an adopted layout, check that product identities match across the registered catalogue and both vaults. During migration, record missing or mismatched legacy product paths as inventory findings; do not require the old tree to match the target before inventory. Require exact identity parity in the final check before enabling the product gate. In single-product mode, the product layout sits directly at the project root in both vaults, and the one README serves as both project and product entry point.

If the project has no accepted target definition, a target path cannot be resolved, or two sources of authority disagree, stop and ask the project lead. A missing or differently named legacy path during migration is an inventory finding to classify under the approved table; it does not block the read-only inventory itself. Do not choose the most convenient target path. Keep product, repository, account, storage, and audience names in the project's definition and settings; never copy machine-specific values from this candidate.

## The placement rules

1. **Secrets and credentials** belong in the project's approved secret store. The account that runs project code cannot read the project secrets tree, and each credential is readable only by the identity that uses it. Never put secrets in source, documents, examples, generated pages, or a migration table.
2. **Named generated reader views** stay in their declared DocsVault locations even though a program writes them. Examples include the product progress page, roadmap, area README pages, module catalogue or high-level module table, and release evidence index. Only each named generator writes its view.
3. **Code and other program data** belong in the configured development store. Tracked source belongs in its repository; temporary work, logs, evidence, caches, and other program output belong in their named temporary or output locations.
4. **Human-authored material for readers** belongs in the configured documents store. Select its product and reader using the project's structure definition.
5. **Cross-product material** belongs in the project-level area named by the definition. A fact has one authoritative home; other pages link to it or are generated from it.
6. **Logs, receipts, and evidence** follow the project's retention and evidence policy. They are not documentation merely because a person may read them.
7. When a kind of file has no destination in the accepted definition, stop and ask the owner. Do not create a new top-level folder to make the problem disappear.

The starter routes in `references/structure.yaml` distinguish management, release records, user guidance, administration guidance, and developer material. Its project-shape rule selects either `<project>/<product>` roots or the project root itself for a single product. The path table there is the only source for folder names and each location's “goes in” and “stays out” rules. Change that definition through an accepted plan before changing consumers or creating a new structural name.

This candidate does not bundle an inventory tool, structure validator, mount doctor, generator, housekeeping service, or copy/delete command. The YAML describes the intended contract; it is not executable enforcement. Git branch, review, and push rules remain in the project's accepted Git policy. This skill only locates clean repository checkouts and temporary work inside the configured development store.

## Keep storage, access, and walks bounded

- **Documents mounts:** when the documents store is one share, check its configured root as a mount separate from the development store and OS root. When each project has its own mount, the documents-store root is a plain parent folder; check each registered project mount separately. Never treat the plain parent as the content device. Run the configured checks at install and service start.
- **Single-disk test hosts:** a root-owned marker created only by test provisioning identifies a test host. The installer never creates it and has no install-time switch to mark a production host as a test host. On a marked test host, the device doctor puts a `WARNING` in its first output line; otherwise the development store sharing the OS device is a failure.
- **Project secrets:** the project-code account cannot read the secrets tree. Grant each credential only to the identity that uses it; a compromised project process must not gain access to every worker's token.
- **Service state:** keep each service's state in its configured service-state location with a service-specific owner and owner-only access. Treat it as secret-bearing data. Never include it in a support bundle or copy it to the cold store except through that service's own approved backup design.
- **Filesystem walks:** inventory, check, move, and housekeeping walks stay within one authorized filesystem, stop at mount boundaries, and never follow symbolic links outside the approved root. A copy between stores names its source and destination explicitly.

## Keep one fact in one place

Update the authoritative home once. Other human-authored pages link to it; named generated views may project it without becoming a second source. Use the exact locations in the project's accepted `structure.yaml` when they differ from these common homes:

| Fact | Canonical home | Other pages |
|---|---|---|
| Project file and folder destinations | Owner-accepted `structure.yaml` | Link to the definition or use its generated views; do not restate its path rules by hand. |
| Current work and release progress | The progress source named by the owner-approved `structure.yaml` | Generated progress and roadmap views may display it; other pages link to the source data. |
| A release's content, state, and date | That release's `plan.md` front matter as defined by the owner-approved `structure.yaml` | Link to the plan or use a generated release view. |
| A decision and its rationale | The decision ledger | Link to the ledger entry. |
| Product identity, name, stage, team, and visibility | The product's `product.yaml` | Link or use an approved generated team view. |
| Audience for each documents area | That area's `audience` in the owner-approved `structure.yaml` | Generated views inherit the area's declared value. |
| A module's purpose and ownership | Its module page | Link or use the generated module catalogue. |

- **One fact, one file.** A page that manually restates a fact with a canonical home is a review finding. Point to the authoritative file; do not create a second copy.
- **Add to the file that exists.** Add a dated heading for a new decision, finding, or day. Create a new file only for a new item named by the structure definition.
- **One current version.** Replace the current file. Keep no side-by-side `-r2`, `.prev`, `-copy`, or `-final` file. Preserve a prior version only through the approved archive process below.
- **A message is not a document.** Use the project's coordination system for handoffs, status notes, and replies.
- **Output is not a document.** Keep generated output, logs, receipts, and evidence in their approved data or evidence locations; keep an index where readers need one.
- **A generated page is written by its generator only.** Do not hand-edit a generated page or maintain a second copy.

The check described by the definition may report identical files, revision-like names, and overfull hand-written folders. A report is evidence for a human decision; it never chooses which file to keep or authorizes deletion.

## Adopt the layout safely

Use `references/adoption.md` for the full adoption sequence and `references/cleanup-method.md` for the four report-and-disposition turns. In brief: do not migrate during a release; inventory read-only; make one disposition row per exact existing path; have the product owner propose and the authorized decision-maker approve the table; preserve repositories, logs, and evidence; move one product at a time; compare counts and hashes; review the move evidence; remove only approved exact paths; then enable a gate for that product after the removals and final check are clean. If a copy cannot be verified, stop before removing the source.

The skill does not run the inventory, write to a storage service, change permissions, update a project map, or remove a path. Those actions need their own approved plan, owner, tools, and checks.

For a network-attached storage (NAS) documents store, confirm its snapshot coverage explicitly. If the product backup does not cover it, the operator guide must require the NAS's own snapshots until a tested backup design closes the gap. Do not infer that a NAS is covered by a cloud provider's snapshots.

## Keep the tree healthy

Use `references/housekeeping.md` for a report-only routine. List stale temporary work, unfinished archive obligations, holds, and new structure breaches with an owner. Keep the report separate from operational state and hand each item to its owner.

**Superseded working-document versions:** when a new version is made, the prior version must leave the active vault for the project's approved cold-store location. Retain it for 14 days (the target); 30 days is the maximum, after which it is deleted. Each product must record the exact class, destination, verification, and expiry in its approved lifecycle table before anyone acts on that rule. This skill does not authorize a deletion, and no file is deleted on the strength of this candidate alone.

**Accepted or shipped evidence:** a proposed 400-day exception for reviewer-accepted or release-shipped evidence remains unconfirmed and is not an active retention rule. Until that decision is confirmed, follow the project's existing approved evidence policy and never sweep evidence into a working-version expiry rule.

No automatic age-based deletion is active in this candidate. A project must review its storage implementation and prove preservation or restore behavior before enabling automation. Any removal must follow the approved per-product table, exact-path recheck, and a recorded receipt.

## Templates and generated views

The bundled templates are starting shapes, not mandatory project facts. Their destination is selected by `structure.yaml`. Named generated reader views stay in DocsVault at their declared locations; other program output stays in DevVault. Keep progress, roadmap, index, and area pages under their named generators. Keep diagrams beside the page they explain, with the source and rendered image together. The wireframes entry in the starter definition names one editable drawing, its same-basename rendered image, and an `index.md` for each screen area. Use the module and product names from the same module catalogue everywhere.

The standard structure names each documents area's audience as `customer-eligible` or `internal`; generated views inherit that value. A release's `released` date is measured from its observed version tag or public release, never typed into the plan. Do not publish or synchronise a folder until the project owner confirms its audience contract and the receiving system's exact read-back behavior.

## Bundled file: references/adoption.md

# Adopting the starter structure

This procedure describes a project migration. It does not authorize one. The project lead must obtain an accepted plan naming the product, paths, owners, schedule, verification, and approver before any write. A product's exact disposition table and the authorized decision-maker's approval are required before moving or removing its files.

## Preconditions

- The product is not in a release run.
- The product owner has selected the versioned `structure.yaml` that will govern the work.
- A read-only inventory can identify every in-scope path, its size, file count, newest write, owner, repository state, and known references.
- The owner-registered product catalogue and intended target shape are known; select the direct project-root product layout only for exactly one registered product. The current legacy tree does not need to match the target before inventory: missing, extra, or differently named product paths are findings to classify.
- Inventory, check, move, and housekeeping walks are constrained to one authorized filesystem, stop at mount boundaries, and never follow symbolic links outside the approved root. Inventory each per-project documents mount separately; do not treat its plain parent folder as a content device.
- The team has a destination for verified copies and a way to preserve the source if verification fails.
- Secrets are excluded from ordinary inventory output or redacted by an approved tool. The project-code account cannot read the project secrets tree, and each credential is readable only by its using identity.

## Sequence

1. **Stop structural growth.** With the project lead's approval, create an empty target skeleton beside the current layout. From the agreed start point, route new files to their approved destination.
2. **Inventory read-only.** List each in-scope top-level folder and its contents without changing permissions, timestamps, or data. Compare the registered product catalogue with the existing product roots in both vaults; record missing, extra, or differently named paths as findings for the disposition table, without requiring parity before this inventory. If documents use per-project mounts, inventory each project mount separately and check each mount's device; do not check the plain documents parent as a content device. Keep each walk on its authorized filesystem, stop at mount boundaries, and do not follow symbolic links outside the root. Record unknown owners as `ask`.
3. **Classify every exact path.** The product lead proposes one fate for each row: `keep`, `move` with a destination, `cold-store`, `remove` as regenerable or finished temporary material, or `ask`. Group identical files and likely revisions for human selection; similarity is not permission to discard either copy.
4. **Approve the table.** The authorized decision-maker approves the exact source and destination paths. Any changed row requires a new review. Do not infer approval from an inventory, check result, or a prior product's table.
5. **Preserve before moving.** Bundle repositories, preserve dirty work, hash and copy evidence according to the evidence policy, and archive logs with a manifest. Keep the source intact until all copy checks pass.
6. **Move one product at a time.** Move complete folders where practical. Compare source and destination file counts and hashes. Record each old-to-new path in one `MOVED.tsv` map so a reader can resolve old references. Keep enumeration on the authorized source filesystem and do not traverse mount points or external symbolic links.
7. **Review the move.** A reviewer checks the move evidence before any approved legacy path is removed. An unverified copy stops the procedure.
8. **Remove only approved rows.** If the table allows removal, an operator runs an inspected procedure that names each exact path. Recheck the path and its contents immediately before removal. A missing or changed path stops the procedure. Record a removal receipt for each completed row.
9. **Check, then gate.** Recheck the product layout and identity parity after approved removals. The project lead enables the structure check for that product only when removals are complete, receipts are reviewed, and the final check is clean. Keep the check in report-only mode for all other products.

## Never

- Migrate during a release run.
- Move a sealed evidence folder file by file.
- Remove a source before the destination copy has been verified.
- Migrate two products at once.
- Delete by wildcard, filename pattern, or age alone.
- Treat identical-content reports as an automatic disposition.
- Let an inventory, check, move, or housekeeping walk cross a mount boundary or follow a symbolic link outside the approved root.
- edit generated files directly or let a project map become a second source of truth.

## Receipt

The return to the project lead records the approved table reference, exact source and destination roots, inventory and move-evidence hashes, counts, verification output, any paths left as `ask`, and the structure-check state. It does not claim the migration passed if any required row is unverified or awaiting approval.

# Clean-up method

Use this method only after the project owner has accepted the structure definition and the authorized decision-maker has approved an exact disposition table. It guides inventory and review; it does not itself authorize a write, move, archive, or deletion.

## The four turns

Work on one product at a time. Keep the inventory read-only until every proposed row has a class, an owner, a destination or hold, and the required approval.

### Turn A — Rebuildable material

List each build output, cache, and dependency tree by exact path, measured size, age, and the build or run that produced it. A name or age alone does not prove that an item is disposable. The owner checks that no process uses the path and that it contains no evidence or untracked work. A lead approves each exact path before its owner removes it, without a force option. Record the command and result.

### Turn B — Exact duplicates

Compare SHA-256 values and list every exact path for each duplicate set. Identify the copy in the approved home. The product owner approves each disposition. Copy and verify before leaving a pointer at a human-facing old path; do not delete a duplicate under this turn.

### Turn C — Superseded versions

Name the exact successor of every candidate and the approved archive or version destination. Follow the project's retention rule. Do not infer an archive destination or deletion date from a filename, timestamp, or apparent age.

### Turn D — Old, unreferenced documents

For each exact path, check the absolute path, relative path, and filename in the relevant scripts, tools, configuration, recent handoffs, and product references. Open each match to decide whether it reads the path, name its owner, and have that owner accept a ready path correction before the move. The product owner decides whether the document is still needed.

## Holds and manifests

Keep an item at its current path when its owner, class, reader, or destination is unknown. Mark it `HOLD`; do not invent a home, create a holding folder, or archive it. The owner must name an approved holding location in the structure and confirm its audience and readers before a copy is made. If no approved location exists, it stays in place with a pointer or a note that names the unresolved owner and question.

For every approved copy or move, record a manifest row containing the exact source path, destination path, class, SHA-256, inventory date, owner, readers, approval reference, and reason. For a sealed evidence bundle, move the whole folder as one unit with its existing sums file; verify all sums after the copy. Do not split a sealed bundle into individual files.

## Consumers and batches

Before a move, search the bounded scope for the exact old absolute path, relative path, and filename. Include launchers, scripts, integration code, configuration, generated-page inputs, and current project references. A pointer does not keep a tool working. Update every path-reading consumer in the same approved batch, or keep the source held until the consumer change is ready. Move a registered Git worktree with Git's worktree command, by its owner; never use a plain filesystem move for it.

Keep each approved batch small enough to verify as one unit. Its manifest records `from`, `to`, class, owner, consumer changes, and SHA-256. After the batch, compare source and destination counts, verify hashes, check the old-path pointers, and run the named consumer checks. Report counts for judged, copied or moved, archived, removed as approved rebuildable material, and not judged. Do not start the next turn until the current batch has a durable receipt and the authorized reviewer has read it.

# The folder structure, explained for people

This page explains how a project's folder structure is designed, how it works day to day, and why it is built this way. It is written for a project owner, a new team member or a reviewer. The other files in this skill are written for AI Workers, the automated agents that do much of the project's work. The exact rules live in `references/structure.yaml`. This page explains them.

Seven terms are used on this page. Each one is defined here once.

| Term | Meaning |
|---|---|
| Vault | One of the two trees of a project: the code vault and the documents vault. Each is a separate mount. |
| Product | One thing the project builds or runs. Each product has its own folders in both vaults. |
| Rebuildable output | Files a tool can produce again from source, such as build output or caches. Its owner may remove it. |
| Record | Evidence of what was run or decided, such as logs, receipts and sealed evidence. A record is moved whole and never edited. |
| Holding place | A folder for content whose home has not been decided yet. Its contents wait there until the lead decides. |
| Manifest | A list of the files in a set, with a hash for each file, so that a copy can be checked. |
| Consumer | Anything that reads a path: a service, a script, a configuration file, a mirror list or a symbolic link. |

## 1. Why a fixed structure

- A person or a worker who opens the project for the first time can find any kind of file without asking, because every kind of file has one home.
- Many workers write into the same project at the same time. Without fixed homes, each one invents a place for its files, and the top level fills with folders that nobody can explain.
- Tools such as build scripts, services, publishing or mirroring jobs and backups read paths. When paths are predictable, the tools stay simple, and a move does not break them silently.
- Source code, temporary work and evidence have different lifetimes. Mixed together, temporary build output hides real work and takes disk space. One project found more than a hundred gigabytes of rebuildable output scattered through its code folder once it looked.
- Documents for readers and code have different audiences and different rules for backup and sharing. Keeping them in two vaults lets each one be shared, mirrored and backed up by its own rule.
- Credentials kept inside a folder that every tool searches get printed by accident. A fixed, separate home for secrets prevents that, and each credential is shared only with the one identity that uses it.
- The same structure in every project means that a worker, a skill or a tool can move between projects without learning where things are again.

## 2. The design in one picture

The code vault holds code and program data. The documents vault holds what people read. Both are shown below, with the level of each entry and what goes in it.

```
Code vault (development store)
<project>/
├── <product>/
│   ├── <repository>/          tracked source and project configuration only
│   └── _work/                 temporary worktrees, release run places, rebuildable output
└── _project/
    ├── tools/                 scripts used across the project's products
    ├── secrets/               credentials, each readable only by the identity that uses it
    ├── home/                  home folder of an operating-system account made for this project
    └── workers/<worker>/      one worker's session files, notes and state

Documents vault (documents store)
<project>/
├── README.md                  entry point that links to each product
├── _project/                  current documents and records shared across products
└── <product>/
    ├── README.md              one-screen entry point for the product
    ├── product.yaml           product identity: id, name, stage, lead, team, visibility
    ├── program/
    │   ├── management/        backlog, team, risks, decisions, generated roadmap
    │   ├── releases/<version>/  plan, progress, notes, checklist, reviews, evidence index
    │   └── progress.yaml      source data for progress; the progress page is generated
    └── docs/
        ├── user/              guides and references for users (customer-eligible)
        ├── admin/             install, upgrade, backup, restore, troubleshooting (customer-eligible)
        └── developer/         design and specs; developer/<topic>/ for one topic (internal)
```

In a project with exactly one product, the product folders sit directly at the project root in both vaults, and the project README also serves as the product README.

Two details matter for daily use. First, the two vaults are separate stores. If a required store is not mounted, the services that depend on it stop rather than write into an empty folder. Second, the secrets folder is readable only by the identity that uses each credential. The account that runs project code cannot read the whole secrets tree, so one compromised process does not expose every worker's token.

## 3. The ideas behind it

**Product first.** Every product has a matching folder in both vaults, and the product is the unit of ownership and access. What several products share lives in one project-level folder, `_project`, so that a fact has one home.

**Two vaults.** The code vault holds code and program data. The documents vault holds what people read. They are separate mounts, so each one can be shared, mirrored and backed up by its own rule.

**Clean source, separate work.** The repository holds only tracked source. Worktrees, test lanes and build output live under `_work`. The repository stays clean, and `_work` can be rebuilt or cleared without touching real work.

**Three audiences for documents.** User guides are for people who use the product. Administrator guides are for people who install, run and restore it. Developer material is for people who change it. Each documents area declares its audience, and generated views inherit that value.

**One definition per project.** A single reviewed file, `structure.yaml`, says which products exist and where the two vaults are. When two people disagree about where a file goes, that file decides. A change to it goes through an accepted plan.

**Settings, not hard-coded paths.** The roots of the vaults are installation settings. The same structure therefore works on another machine or on another mount, and no machine-specific path is written into the skill.

## 4. How it works day to day

When you have a new file, place it by asking these questions in order. The first question that matches gives the home.

1. Is it a secret or a credential? It goes to the project's approved secret store.
2. Is it a generated reader view that the definition names? It stays in its declared place in the documents vault. Only the named generator writes it, even though a program produces it.
3. Does a program read or produce it? Tracked source goes in the repository. Other program data and output go in the named temporary or output area.
4. Is it human-written material for a reader? It goes in the product's documents area, or in the project-level area if several products share it.
5. Which reader needs it? Management, release, user, administrator or developer material each has its own area.
6. If no route fits, stop and ask the project owner. Do not invent a folder.

The day-to-day rules follow from these questions:

- **Never create a new top-level folder** to hold something that has no home. Ask the lead, and let the definition be revised if the new kind of file is real.
- **Keep a worker's own notes in that worker's folder**, under `_project/workers/<worker>/`. Do not write into another worker's folder.
- **Keep build output and temporary checkouts under `_work`.** The repository holds only tracked source.
- **Keep credentials in the secrets folder only.** They never go into source, documents, examples or generated pages.
- **Revise a document in place.** Replace the current file. Do not keep a copy named `-v2`, `-final` or `-copy` beside it. An older version is archived to the approved place, under the approved rule.
- **Keep one fact in one file.** Link to the authoritative page instead of copying the fact into another page. A page that restates a fact with a home somewhere else is a review finding.
- **Add to the file that exists.** A new decision, finding or day becomes a dated heading in the file that already holds that kind of record. A new file is created only for an item that the definition names.
- **Leave generated pages to their generator.** Do not edit a generated page by hand, and do not keep a second copy of it.
- **Name the folder when you search.** Never search from a vault's root. A search from the root is slow on a shared machine and reaches folders that you should not read.
- **Read a duplicate report as a question, not an answer.** The structure check reports identical files, revision-like names and hand-written folders that have grown too full. The report is evidence for a person to decide. It does not choose which copy to keep, and it does not authorize a deletion.
- **Expect a periodic housekeeping report.** It lists stale temporary work, unfinished archive duties, holds and new structure findings, each with the owner who must act. It is report-only. An expired hold is reported as expired, and nobody clears it silently.

## 5. Adopting it in an existing project

Adoption changes files that people and tools already use, so it is done with care. The stages below describe the method in plain words. The full method is in `references/adoption.md` and `references/cleanup-method.md` of the same skill.

- **Pause the work.** Do not migrate while a release is being run. Start the migration only from an agreed starting point.
- **Write the project's definition.** The owner chooses the version of `structure.yaml` that will govern the work and records it as the project's accepted definition.
- **Map every existing folder.** A read-only inventory lists each folder, its size, its files, its owner and the consumers that refer to it. Nothing is changed during this step.
- **Record every unknown owner as ask.** If nobody can say who owns a path, that row is not guessed. It waits until the owner is found.
- **Decide the fate of each row.** The product's lead proposes one fate for each exact path. The fate is one of these: stays at a home, moves to a named destination, is rebuildable, is a record, is a secret, stays where a tool reads it, or goes to a holding place because nobody can judge it yet. An authorized person approves the table.
- **Remove rebuildable output first.** It has no unique content, and removing it makes the rest of the inventory easier to read. Each removal is recorded.
- **List every consumer.** Find everything that reads a path that will move: services, scripts, configuration, mirror lists, and symbolic links, both absolute and relative.
- **Move one product at a time.** Rename complete folders where possible. Repair git worktrees with git's own command, not by hand. Re-make the links, and change the consumers in the same batch as the move.
- **Move secrets as a separate, reviewed step.** Credentials never travel with ordinary files, and they are never copied into an inventory or a table.
- **Keep the source until the copy is proven.** The original stays in place until every copy check has passed.
- **Verify before removing anything.** Compare file counts and hashes at the destination. Keep the source intact until every copy check passes. A copy that cannot be verified stops the procedure.
- **Check the result with an independent reader.** A reviewer who did not do the move compares the result with the definition.
- **Record the outcome.** The lead's report names the approved table, the exact source and destination, the hashes and counts, the verification output and any path still marked as ask. A migration is not called passed while a required row is unverified or still waiting for approval.
- **Resume the work.** Enable the structure check for the product only after the removals and the final check are clean. Other products keep the check in report-only mode until their own turn.

## 6. What the structure does not do

- Installing the skill does not move any file. A move needs the owner's decision and the adoption method above.
- It does not delete anything. Only rebuildable output is removed, and only by its owner, after an approved plan.
- It does not replace version control, backups or access control. Each of those keeps its own rules.
- It does not replace the project's own approved rules. Git branch, review and push rules, and access rules, stay with the project's accepted policies.
- It does not check anything on its own. The rules are a contract that people and tools follow. Nothing in the skill enforces them automatically.
- It does not turn on automatic deletion. No age-based removal is active. Any future automation needs an owner's decision, a tested restore check and a recorded receipt first.
- It does not work the same way on every platform. Mount behavior, permission labels and executable-file behavior must be tested on each supported host. Until a project has run that test, the results on its platforms are not proven.

## 7. Common questions

**Where do I put a file that fits two products?**
In the project-level `_project` folder, in the same program or docs area that a product would use. Put the fact there once and link to it from both products.

**What if no home fits?**
Put the file in a holding place and ask the lead. The lead decides the home. If the new kind of file is real and will recur, the definition is revised through an accepted plan.

**Can a product add its own subfolders?**
Yes, inside the homes that the definition gives. No, not at the top level. A new top-level entry needs a reviewed change to the definition.

**Why may I not search the whole vault?**
A search from the root is slow on a shared machine. It also reaches folders that are not yours to read, such as credentials and other workers' private state. Name the folder you need.

**What is a record, and why is it not edited?**
A record is evidence of what was run or decided, such as logs, receipts and sealed evidence. Its value depends on it being unchanged. A record is moved whole, with its manifest, and it is never rewritten.

**Who decides?**
The product's lead decides for the product's folders. The project's owner decides on the definition, `structure.yaml`, and on any move or removal that the definition does not already settle.
