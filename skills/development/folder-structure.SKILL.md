# Folder structure

This skill gives a project a single, readable definition of where its work belongs. It helps a worker classify a new file and gives a project lead a safe process for adopting the layout. It is a portable candidate: it does not replace the project's own approved rules, grant file access, or perform a migration.

## Start with the project's authority

Before creating or moving a project file, read the project's current `structure.yaml`, the accepted plan for the change, the project root and product catalogue registered by its owner, and the selected project shape. The bundled `references/structure.yaml` is a starter definition, not proof that a project adopted it. A project may use it only after its owner approves the layout and records the effective definition in the project's normal source of truth. Select `single_product` only when exactly one product is registered; otherwise use `multi_product`. For ordinary placement in an adopted layout, check that product identities match across the registered catalogue and both vaults. During migration, record missing or mismatched legacy product paths as inventory findings; do not require the old tree to match the target before inventory. Require exact identity parity in the final check before enabling the product gate. In single-product mode, the product layout sits directly at the project root in both vaults, and the one README serves as both project and product entry point.

If the project has no accepted target definition, a target path cannot be resolved, or two sources of authority disagree, stop and ask the project lead. A missing or differently named legacy path during migration is an inventory finding to classify under the approved table; it does not block the read-only inventory itself. Do not choose the most convenient target path. Keep product, repository, account, storage, and audience names in the project's definition and settings; never copy machine-specific values from this candidate.

## The placement rules

1. **Secrets and credentials** belong in the project's approved secret store. The account that runs project code cannot read the project secrets tree, and each credential is readable only by the identity that uses it. Never put secrets in source, documents, examples, generated pages, or a migration table.
2. **Named generated reader views** stay in their declared DocsVault locations even though a program writes them. Examples include the product progress page, roadmap, area README pages, module catalogue or high-level module table, and release evidence index. Only each named generator writes its view.
3. **Code and other program data** belong in the configured development store. Tracked source belongs in its repository; temporary work, logs, evidence, caches, and other program output belong in their named temporary or output locations.
4. **Human-authored material for readers** belongs in the configured documents store. Select its product and reader using the project's structure definition.
5. **Cross-product material** belongs in the project-level area named by the definition. A fact has one authoritative home; other pages link to it or are generated from it.
6. **Logs, receipts, and evidence** follow the project's retention and evidence policy. They are not documentation merely because a person may read them.
7. When a kind of file has no destination in the accepted definition, stop and ask the owner. Do not create a new top-level folder to make the problem disappear.

The starter routes in `references/structure.yaml` distinguish management, release records, user guidance, administration guidance, and developer material. Its project-shape rule selects either `<project>/<product>` roots or the project root itself for a single product. The path table there is the only source for folder names and each location's “goes in” and “stays out” rules. Change that definition through an accepted plan before changing consumers or creating a new structural name.

This candidate does not bundle an inventory tool, structure validator, mount doctor, generator, housekeeping service, or copy/delete command. The YAML describes the intended contract; it is not executable enforcement. Git branch, review, and push rules remain in the project's accepted Git policy. This skill only locates clean repository checkouts and temporary work inside the configured development store.

## Keep storage, access, and walks bounded

- **Documents mounts:** when the documents store is one share, check its configured root as a mount separate from the development store and OS root. When each project has its own mount, the documents-store root is a plain parent folder; check each registered project mount separately. Never treat the plain parent as the content device. Run the configured checks at install and service start.
- **Single-disk test hosts:** a root-owned marker created only by test provisioning identifies a test host. The installer never creates it and has no install-time switch to mark a production host as a test host. On a marked test host, the device doctor puts a `WARNING` in its first output line; otherwise the development store sharing the OS device is a failure.
- **Project secrets:** the project-code account cannot read the secrets tree. Grant each credential only to the identity that uses it; a compromised project process must not gain access to every worker's token.
- **Service state:** keep each service's state in its configured service-state location with a service-specific owner and owner-only access. Treat it as secret-bearing data. Never include it in a support bundle or copy it to the cold store except through that service's own approved backup design.
- **Filesystem walks:** inventory, check, move, and housekeeping walks stay within one authorized filesystem, stop at mount boundaries, and never follow symbolic links outside the approved root. A copy between stores names its source and destination explicitly.

## Keep one fact in one place

Update the authoritative home once. Other human-authored pages link to it; named generated views may project it without becoming a second source. Use the exact locations in the project's accepted `structure.yaml` when they differ from these common homes:

| Fact | Canonical home | Other pages |
|---|---|---|
| Project file and folder destinations | Owner-accepted `structure.yaml` | Link to the definition or use its generated views; do not restate its path rules by hand. |
| Current work and release progress | The registered progress data | Generated progress and roadmap views may display it; other pages link to the data. |
| A release's content, state, and date | That release plan's front matter | Link to the plan or use a generated release view. |
| A decision and its rationale | The decision ledger | Link to the ledger entry. |
| Team membership and roles | The product's `product.yaml` | Link or use an approved generated team view. |
| A module's purpose and ownership | Its module page | Link or use the generated module catalogue. |

- **One fact, one file.** A page that manually restates a fact with a canonical home is a review finding. Point to the authoritative file; do not create a second copy.
- **Add to the file that exists.** Add a dated heading for a new decision, finding, or day. Create a new file only for a new item named by the structure definition.
- **One current version.** Replace the current file. Keep no side-by-side `-r2`, `.prev`, `-copy`, or `-final` file. Preserve a prior version only through the approved archive process below.
- **A message is not a document.** Use the project's coordination system for handoffs, status notes, and replies.
- **Output is not a document.** Keep generated output, logs, receipts, and evidence in their approved data or evidence locations; keep an index where readers need one.
- **A generated page is written by its generator only.** Do not hand-edit a generated page or maintain a second copy.

The check described by the definition may report identical files, revision-like names, and overfull hand-written folders. A report is evidence for a human decision; it never chooses which file to keep or authorizes deletion.

## Adopt the layout safely

Use `references/adoption.md` for the full sequence. In brief: do not migrate during a release; inventory read-only; make one disposition row per exact existing path; have the product owner propose and the authorized decision-maker approve the table; preserve repositories, logs, and evidence; move one product at a time; compare counts and hashes; review the move evidence; remove only approved exact paths; then enable a gate for that product after the removals and final check are clean. If a copy cannot be verified, stop before removing the source.

The skill does not run the inventory, write to a storage service, change permissions, update a project map, or remove a path. Those actions need their own approved plan, owner, tools, and checks.

For a network-attached storage (NAS) documents store, confirm its snapshot coverage explicitly. If the product backup does not cover it, the operator guide must require the NAS's own snapshots until a tested backup design closes the gap. Do not infer that a NAS is covered by a cloud provider's snapshots.

## Keep the tree healthy

Use `references/housekeeping.md` for a report-only routine. List stale temporary work, unfinished archive obligations, holds, and new structure breaches with an owner. Keep the report separate from operational state and hand each item to its owner.

**Superseded working-document versions:** when a new version is made, the prior version must leave the active vault for the project's approved cold-store location. Retain it for 14 days (the target); 30 days is the maximum, after which it is deleted. Each product must record the exact class, destination, verification, and expiry in its approved lifecycle table before anyone acts on that rule. This skill does not authorize a deletion, and no file is deleted on the strength of this candidate alone.

**Accepted or shipped evidence:** a proposed 400-day exception for reviewer-accepted or release-shipped evidence remains unconfirmed and is not an active retention rule. Until that decision is confirmed, follow the project's existing approved evidence policy and never sweep evidence into a working-version expiry rule.

No automatic age-based deletion is active in this candidate. A project must review its storage implementation and prove preservation or restore behavior before enabling automation. Any removal must follow the approved per-product table, exact-path recheck, and a recorded receipt.

## Templates and generated views

The bundled templates are starting shapes, not mandatory project facts. Their destination is selected by `structure.yaml`. Named generated reader views stay in DocsVault at their declared locations; other program output stays in DevVault. Keep progress, roadmap, index, and area pages under their named generators. Keep diagrams beside the page they explain, with the source and rendered image together. Use the module and product names from the same module catalogue everywhere.

Audience and visibility for any generated project view must come from the project's approved metadata. Do not publish or synchronise a folder until the project owner confirms its audience contract and the receiving system's exact read-back behavior.

Keep such items marked **not tested** until the named project test produces evidence and its owner accepts the result. ## Bundled file: references/adoption.md

# Adopting the starter structure

This procedure describes a project migration. It does not authorize one. The project lead must obtain an accepted plan naming the product, paths, owners, schedule, verification, and approver before any write. A product's exact disposition table and the authorized decision-maker's approval are required before moving or removing its files.

## Preconditions

- The product is not in a release run.
- The product owner has selected the versioned `structure.yaml` that will govern the work.
- A read-only inventory can identify every in-scope path, its size, file count, newest write, owner, repository state, and known references.
- The owner-registered product catalogue and intended target shape are known; select the direct project-root product layout only for exactly one registered product. The current legacy tree does not need to match the target before inventory: missing, extra, or differently named product paths are findings to classify.
- Inventory, check, move, and housekeeping walks are constrained to one authorized filesystem, stop at mount boundaries, and never follow symbolic links outside the approved root. Inventory each per-project documents mount separately; do not treat its plain parent folder as a content device.
- The team has a destination for verified copies and a way to preserve the source if verification fails.
- Secrets are excluded from ordinary inventory output or redacted by an approved tool. The project-code account cannot read the project secrets tree, and each credential is readable only by its using identity.

## Sequence

1. **Stop structural growth.** With the project lead's approval, create an empty target skeleton beside the current layout. From the agreed start point, route new files to their approved destination.
2. **Inventory read-only.** List each in-scope top-level folder and its contents without changing permissions, timestamps, or data. Compare the registered product catalogue with the existing product roots in both vaults; record missing, extra, or differently named paths as findings for the disposition table, without requiring parity before this inventory. If documents use per-project mounts, inventory each project mount separately and check each mount's device; do not check the plain documents parent as a content device. Keep each walk on its authorized filesystem, stop at mount boundaries, and do not follow symbolic links outside the root. Record unknown owners as `ask`.
3. **Classify every exact path.** The product lead proposes one fate for each row: `keep`, `move` with a destination, `cold-store`, `remove` as regenerable or finished temporary material, or `ask`. Group identical files and likely revisions for human selection; similarity is not permission to discard either copy.
4. **Approve the table.** The authorized decision-maker approves the exact source and destination paths. Any changed row requires a new review. Do not infer approval from an inventory, check result, or a prior product's table.
5. **Preserve before moving.** Bundle repositories, preserve dirty work, hash and copy evidence according to the evidence policy, and archive logs with a manifest. Keep the source intact until all copy checks pass.
6. **Move one product at a time.** Move complete folders where practical. Compare source and destination file counts and hashes. Record each old-to-new path in one `MOVED.tsv` map so a reader can resolve old references. Keep enumeration on the authorized source filesystem and do not traverse mount points or external symbolic links.
7. **Review the move.** A reviewer checks the move evidence before any approved legacy path is removed. An unverified copy stops the procedure.
8. **Remove only approved rows.** If the table allows removal, an operator runs an inspected procedure that names each exact path. Recheck the path and its contents immediately before removal. A missing or changed path stops the procedure. Record a removal receipt for each completed row.
9. **Check, then gate.** Recheck the product layout and identity parity after approved removals. The project lead enables the structure check for that product only when removals are complete, receipts are reviewed, and the final check is clean. Keep the check in report-only mode for all other products.

## Never

- Migrate during a release run.
- Move a sealed evidence folder file by file.
- Remove a source before the destination copy has been verified.
- Migrate two products at once.
- Delete by wildcard, filename pattern, or age alone.
- Treat identical-content reports as an automatic disposition.
- Let an inventory, check, move, or housekeeping walk cross a mount boundary or follow a symbolic link outside the approved root.
- edit generated files directly or let a project map become a second source of truth.

## Receipt

The return to the project lead records the approved table reference, exact source and destination roots, inventory and move-evidence hashes, counts, verification output, any paths left as `ask`, and the structure-check state. It does not claim the migration passed if any required row is unverified or awaiting approval.

## Bundled file: references/housekeeping.md

# Report-only housekeeping routine

This routine keeps the adopted structure visible. It lists and routes work; it does not remove files. Run it only against roots and products authorized by the project owner. Constrain each inventory or housekeeping walk to one authorized filesystem, stop at mount boundaries, and never follow symbolic links outside the approved root. Where documents are mounted per project, run the check for each project mount; the plain documents parent is not a content device.

## Daily or event-driven report

For each product, collect from its registered roots only:

1. Free space in configured development and documents stores, with the source of each measurement.
2. Every temporary work entry with owner, age, branch or run state, and whether its work is merged or closed.
3. Obligations left by recent events: merged work whose temporary directory remains, ended runs whose logs lack an archive manifest, or replaced documents not handled under an approved archive policy.
4. Holds and their expiry dates; report an expired hold as expired, never silently clear it.
5. New structure-check findings, including identical contents, revision-like names, and overfull hand-written folders.
6. A line for each owner who needs to act, routed through the project's coordination system.
7. A separate list of candidate rebuildable material for the project lead and operator to review.

Use the template in `../templates/housekeeping.md`. Keep generated measurements separate from operational state and do not type them into a plan as a second source of truth.

## Archive and removal boundary

For anything a project has approved to keep: list it, copy it with a manifest, verify the copy by hash, record its destination, and only then consider removing the exact source path under the approved table.

When a new working-document version is made, the superseded version must leave the active vault for the project's approved cold-store location. The target retention is 14 days; 30 days is the maximum, after which the version is deleted. Each product must approve a table naming exact classes, destination, verification, and expiry before anyone acts on this rule. This report-only routine does not authorize deletion, and nothing is deleted on the strength of this candidate alone.

A proposed 400-day exception for reviewer-accepted or release-shipped evidence remains unconfirmed and is not an active retention rule. Until confirmed, accepted or shipped evidence follows the project's existing approved evidence policy and is never swept into a working-version expiry rule.

No automatic age-based deletion is active in this candidate. Before enabling automation, the project owner must approve exact classes and retention, the operator must review the storage implementation, and a restore or preservation check must pass. Every removal follows the approved per-product table, exact-path recheck, and a recorded receipt.

Temporary files, caches, build output, branches, and worktrees are not automatically safe to remove. A project may automate a narrowly named class only after an approved plan, tested predicate, exact-path recheck, and removal receipt exist. A worker does not remove another worker's active folder.
